# E4 — Фазы, полярность и контракт награды

Статус: **построено и измерено. PASS на контролируемом семействе. Главный вывод —
асимметричный и, вероятно, неудобный: отрицательную полярность доказать изнутри
эмулятора можно, положительную — нельзя.**

- Модули: `app/src/main/assets/lab/agod-goals.js`, `app/src/main/assets/lab/agod-reward.js`
  (оба новые, **ничем в продакшене не импортируются**)
- Проверка: `tools/agod_reward_check.cjs`
- Данные: `logs/reward_report.json`, лог `logs/agod_reward_check.log`
- Существующих файлов GU не изменено ни одного

## 1. Почему понадобились новые модули

`objective-profiles.js` по построению запрещает что-либо, кроме `role:'unknown'`,
`polarity:'unknown'`, `confidence:null`, и отвергает любую попытку заявить
independence или holdout. Для PR1 это правильно, но означает, что существующий
формат **не способен нести** проверенную цель. Менять его нельзя (правила изоляции),
поэтому E4 реализован отдельными экспериментальными модулями — как и предусматривает
§4.2 (`agod-phases`, `agod-goals`, `agod-reward`).

## 2. Асимметрия полярности — центральный результат

### 2.1. Что можно доказать: NEGATIVE

Измерено на картридже (seed 0), без участия оракула:

| Шаг | lives | score | эффект положительной кнопки |
|---|---:|---:|---|
| начало | 3 | 250 | счёт меняется |
| импульс «отрицательной» кнопки ×1 | 2 | 250 | меняется |
| ×2 | 1 | 250 | меняется |
| ×3 | **0** | 250 | — |
| ×4…×6 | 0 (пол) | 250 | — |
| после исчерпания | 0 | 250 | **счёт больше не меняется** |

Цепочка, каждое звено которой наблюдаемо: действие **монотонно уменьшает** переменную
→ переменная **упирается в пол** → на полу **все ранее подтверждённые причинные
эффекты перестают воспроизводиться**. Именно это делает изменение вредным в терминах
самой игры, а не просто «числом вниз». Такая цепочка даёт `NEGATIVE`.

### 2.2. Что доказать нельзя: POSITIVE

Накопитель, который действие увеличивает, **никогда** не получает `POSITIVE` и
никогда не доходит до `VERIFIED`. Он остаётся `CANDIDATE` с `polarity:'UNKNOWN'` и
явным флагом `positiveClaimBlocked`.

Обоснование простое: изнутри эмулятора ничто не отличает «счёт» от «счётчика,
который просто растёт». Объявить рост наградой — это ровно тот запрещённый ярлык из
§1.3 («присвоение награды каждому увеличению счётчика»). Поэтому здесь стоит
принципиальный блок, а не эвристика с порогом уверенности.

Практическое следствие для проекта: **положительная награда не может быть получена
автоматически только из наблюдения за RAM.** Для неё нужен внешний источник истины —
независимый оракул (§11.2), человеческая разметка на этапе калибровки, или
подтверждение через holdout-раздел реестра. Это ограничение метода, а не недоработка
реализации.

### 2.3. Результат против оракула

7 картриджей, оракул читается только после выдачи гипотез:

| Метрика | Результат |
|---|---|
| `NEGATIVE` восстановлена у правильной кнопки | **7 / 7** |
| Накопитель объявлен `POSITIVE` | **0 / 7** (блокировано по построению) |
| Накопитель дошёл до `VERIFIED` | **0 / 7** |
| Фаза `PLAYING` при живой игре | **7 / 7** |
| Фаза `DEATH` после исчерпания | **7 / 7** |

## 3. Фазы (AGOD-06)

Фаза выводится из **совокупности** сигналов, а не из одного RAM-флага:
воспроизводимость ранее подтверждённых эффектов, состояние ресурса и обратимость
подавления тем же действием.

- эффекты воспроизводятся → `PLAYING`
- подавлены, но то же действие их возвращает → `MENU`
- подавлены, ресурс исчерпан и упёрся в пол → `DEATH`
- подавлены, но ни обратимость, ни исчерпание не объясняют → `UNKNOWN`

**Честная граница метода.** Картридж продолжает писать эхо нажатой кнопки в RAM даже
«после смерти», поэтому критерий «исчезли все подтверждённые эффекты» неверен:
служебная проводка ввода не исчезает никогда. Подавление измеряется по области
адресов, которую задаёт вызывающая сторона (берётся из причинного движка, не из
оракула). **Отделять служебный ввод от игрового состояния в общем виде здесь не
решено**, и область — это явная граница честности, а не скрытая эвристика.

## 4. Брокер подтверждённой награды (§6)

Единственный путь, по которому может появиться число — `claim()` при выполнении
всех условий. Любой отказ возвращает `UNKNOWN` или `INVALIDATED`, и **ни один
отказ не возвращает 0**.

### 4.1. Контракт UNKNOWN

Пакет со статусом `UNKNOWN` **не содержит ключа `value` вообще**. Это не ноль и не
null: отсутствующий ключ нельзя привести к числу так, как приводится 0. Проверено
отдельно, включая round-trip через JSON:

| Проверка | Результат |
|---|---|
| статус | `UNKNOWN` |
| есть ключ `value` | нет |
| есть ключ `value` после JSON round-trip | нет |
| приводится к числу | нет (`undefined`) |

### 4.2. Восемь негативных тестов §6.3 — все пройдены

| Кейс §6.3 | Ожидалось | Получено |
|---|---|---|
| 1. бесконечный рост счётчика без игрового успеха | UNKNOWN | UNKNOWN |
| 2. повторное начисление одного события | INVALIDATED | INVALIDATED |
| 3. награда за таймер/анимацию | UNKNOWN | UNKNOWN |
| 4. ложная победа после pause/menu | INVALIDATED | INVALIDATED (и menu, и pause) |
| 5. искусственная награда после save/load | INVALIDATED | INVALIDATED |
| 6. награда от восстановленного контрольного эпизода | INVALIDATED | INVALIDATED |
| 7. эксплуатация визуального артефакта | UNKNOWN | UNKNOWN (источник не разрешён) |
| 8. противоречие RAM и игрового результата | INVALIDATED | INVALIDATED (цель отозвана) |

Дополнительно проверено сверх списка ТЗ (всего 17 кейсов): исполненная маска ≠
запрошенной → INVALIDATED; вмешательство человека → INVALIDATED; незавершённый
интервал → UNKNOWN; устаревший исход → UNKNOWN; чужой контекст ROM/ядра →
INVALIDATED; устаревшая ревизия профиля → UNKNOWN; нулевая величина → UNKNOWN.

Во **всех** неуспешных случаях ключ `value` отсутствует.

### 4.3. Разделение каналов

Внутренняя мотивация (novelty и подобное) возвращается под ключом `intrinsicValue`
в канале `intrinsic` и **не имеет ключа `value`** — сложить её с игровой наградой по
неосторожности нельзя. Это требование §6.2 о разделении игровой и исследовательской
мотивации.

## 5. Чего E4 НЕ сделал

1. **`VERIFIED` не достижим изнутри этих модулей.** Повышение до `VERIFIED` требует
   holdout-доказательств из реестра (AGOD-08/09), а реестра нет — он не реализован.
   В тестах брокера `VERIFIED`-цель подаётся как фикстура, чтобы проверить сам
   контракт выплаты, а не чтобы заявить, что такую цель уже умеют получать.
2. **EvidenceRegistry (AGOD-08) не построен**: группы DISCOVERY/CALIBRATION/HOLDOUT/
   EXCLUDED, учёт пересечения стартов и повторного использования данных — отсутствуют.
3. Жизненный цикл реализован частично: `CANDIDATE → TESTING → CALIBRATED` работает,
   переходы `CONTRADICTED/INVALIDATED/EXPIRED` в индукции не используются (отзыв цели
   живёт в брокере).
4. Калибровка уверенности не делалась: `confidence` всегда `null`,
   `calibrationStatus:'uncalibrated'`.
5. Всё измерено на одном синтетическом семействе. Blind-корпус §11.1 не существует.
6. Android не затронут; стоимость индукции на устройстве не измерялась.
7. Визуальный HUD (AGOD-03) не делался — E2 по-прежнему не продвинут.
