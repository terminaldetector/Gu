# E1 — Аудит внешних исходников

Статус: **E1 закрыт для четырёх проектов с указанными в ТЗ SHA. Три проекта без SHA не аудировались.**
Ни одна строка чужого кода в GU не перенесена. Решения — рекомендации, не внедрение.

Машинно-читаемая версия со всеми SHA256, путями и обоснованиями: `source_manifest.json`.

## 1. Метод

ТЗ §9 требует анализа реальных исходных файлов, а не README, и повторной проверки SHA
перед переносом. Выполнено именно так:

1. Каждый SHA из ТЗ проверен на существование в указанном репозитории (HTTP-запрос к
   `raw.githubusercontent.com` на этом коммите).
2. Файлы получены на зафиксированном SHA (blobless shallow fetch или прямая загрузка).
3. Файлы прочитаны. Выводы ниже сделаны по коду, не по описаниям.
4. Для каждого файла посчитан SHA256, зафиксирована лицензия.

## 2. Проверка SHA и путей — главный результат раздела

Все четыре SHA **существуют**. Но **пути, подразумеваемые ТЗ, в двух случаях из четырёх
не существуют на этих коммитах**:

| Проект | SHA существует | Путь из ТЗ | Фактический путь |
|---|---|---|---|
| OCAtari | да | путь не указан | `scripts/find_causative_ram_full.py` |
| rcheevos | да | подразумевался `src/rcheevos/*.c` | **`src/runtime/rc_condition.c`, `rc_memref.c`, `rc_trigger.c`, `rc_lboard.c`** |
| Stable-Retro | да | подразумевался `retro/retro_env.py` | **`stable_retro/retro_env.py`** (пакет переименован), `compute_step` на строке 381 |
| Stable-Baselines3 | да | `stable_baselines3/dqn/dqn.py`, `common/buffers.py` | совпал |

Это ровно то, ради чего ТЗ требовал перепроверку: планировать перенос по путям из
задания было бы нельзя.

## 3. Лицензии

Все четыре проекта — **MIT**. Лицензионной несовместимости с GU (MIT) нет ни у одного.
Поскольку код не копировался, обязательств по атрибуции пока не возникло; они возникнут
в момент фактического переноса и должны быть оформлены тогда же.

## 4. Что эти механизмы на самом деле делают

### 4.1. OCAtari `find_causative_ram` — ближайший внешний аналог недостающей причинности

Реальный алгоритм: для каждого адреса RAM — сброс среды с фиксированным seed,
**запись значения в этот адрес** через `ale.setRAM(i, v)`, один шаг, подсчёт изменившихся
блоков изображения относительно эталонного кадра. Адрес попадает в кандидаты, если
изменений «мало, но не ноль» (от 2 до 59 блоков).

Что это значит для GU:

- Это **настоящее вмешательство**, а не корреляция — то есть концептуально именно то,
  чего не хватает в E3/AGOD-05.
- Но вмешательство идёт **записью в RAM**, тогда как AGOD-05 описывает вмешательство
  **действиями** (action / no-op / alternative / sham). Это другой, более сильный зонд.
- Он связывает RAM с **изображением** — это прямо закрывает часть разрыва §2.4
  (RAM → Video), и пересекается с AGOD-03.
- Он **не определяет** ни цель, ни полярность, ни награду. Только «этот адрес видимо
  влияет на экран».
- Качество кода — исследовательский скрипт: зависимости gymnasium/ALE/matplotlib/tqdm,
  собственный docstring говорит «rough idea», и есть захардкоженный игро-специфичный
  хак `setRAM(123, 60)`.

**Решение: PROTOTYPE.** Переносить метод, не код, и только в изолированную песочницу
воспроизведения. Запись в RAM требует отдельного контракта безопасности: §13.2 запрещает
трогать живую игру пользователя.

### 4.2. rcheevos — зрелый движок предикатов по памяти

Реальный механизм: типизированные memref (размер, формат, дельта к предыдущему значению),
условия со сравнением, цепочки `ADD_SOURCE` / `SUB_SOURCE` / `ADD_ADDRESS` (разыменование
указателей), `REMEMBER`, `MEASURED`, счётчики попаданий, автоматы триггеров и лидербордов.

Чистый C, без внешних зависимостей, MIT, с собственными тестами (`test/runtime/`).
Модель данных близка к `GoalHypothesis.predicate` из AGOD-07 и к жизненному циклу AGOD-09.

Ограничение, которое нельзя обойти: **движок вычисляет предикаты, но не находит их**.
Весь контент RetroAchievements пишется людьми под каждую игру — это ровно та ручная
разметка, которую §1.3 запрещает как продуктовый механизм.

**Решение: PROTOTYPE.** Брать можно как исполнитель предикатов, но только вместе с
GU-генератором этих предикатов. До ADOPT нужно измерить стоимость интеграции C на
Android (JNI либо WASM-сборка) — сейчас в GU нет ни того, ни другого.

### 4.3. Stable-Retro — это оракул, а не механизм обнаружения

`compute_step` — обёртка в семь строк: возвращает `(reward, done, info)` из `GameData`.
Существо — в C++ (`src/data.cpp`): награда и терминальность загружаются из
**рукописного манифеста сценария** на каждую игру — `reward.variables` с коэффициентами,
`reward.time`, опциональный Lua-скрипт, `done.variables`.

То есть источник смысла здесь — ручная разметка под каждый ROM. Для пути обнаружения
это дисквалифицирующее свойство.

**Решение: REJECT для пути обнаружения / кандидат ADOPT как оракул.** §11.2 прямо
разрешает ручную разметку для независимой проверки качества — и для этой роли
stable-retro подходит хорошо. Его декларативная схема сценария — удачный образец для
формата объявления подтверждённой награды в GU.

### 4.4. Stable-Baselines3 — и здесь расхождение с ТЗ

`DQN.train` на этом SHA: выборка из replay; под `no_grad` цель считается как максимум
Q по **target-сети**; 1-шаговая TD-цель `r + (1-done)·γ·maxQ'`; `gather` текущих Q по
выполненным действиям; Huber-лосс; `zero_grad` → `backward` → `clip_grad_norm` →
`optimizer.step`; периодическая синхронизация target через polyak.

**Это ванильный DQN, а не Double DQN.** Слово `double` в `dqn.py` на этом коммите не
встречается вовсе. Double DQN выбирал бы argmax онлайн-сетью и оценивал его target-сетью.
ТЗ §NN-01 требует именно Double DQN — значит, эту часть придётся писать, а не переносить,
и называть результат «портом Double DQN из SB3» будет неверно.

Второе: SB3 на PyTorch. Для Android/WebView-рантайма GU он неприменим как есть, поэтому
вопрос §8.2 (LiteRT / ONNX / ExecuTorch / собственный backend) этим источником **не
закрывается**.

**Решение: PROTOTYPE.** Структура шага обучения — правильный скелет под чек-лист NN-04
и должна быть воспроизведена. Но Double-DQN-цель пишется самостоятельно, а рантайм
остаётся открытым вопросом.

## 5. Не аудировано

TorchRL, DreamerV3, Dopamine — ТЗ не даёт SHA («SHA определить»). В этом проходе они не
пинились и не читались. Никаких утверждений о них не делается.

## 6. Сводка решений

| Проект | Решение | Коротко |
|---|---|---|
| OCAtari `find_causative_ram` | **PROTOTYPE** | метод причинного вмешательства ценен; код непортируем, запись в RAM требует песочницы и контракта безопасности |
| rcheevos | **PROTOTYPE** | отличный портируемый движок предикатов; не решает задачу обнаружения; нужна оценка JNI/WASM |
| Stable-Retro | **REJECT** (обнаружение) / кандидат в оракулы | награда рукописная под каждую игру; как оракул §11.2 — уместен |
| Stable-Baselines3 | **PROTOTYPE** | скелет шага обучения — да; Double DQN писать самим; рантайм-вопрос не закрыт |

ADOPT NOW: **ноль**. На основании прочитанного кода ни один механизм не готов к прямому
внедрению без прототипа и измерений — что соответствует требованию §9 не переносить код
только из-за технической пригодности.

## 7. Что это меняет в плане работ

1. Причинный слой (E3) придётся строить самим: ближайший внешний аналог — зонд
   «RAM → изображение», а ТЗ требует зонд «действие → исход». Это разные механизмы, и
   второй внешнего прототипа не имеет.
2. Формат предикатов стоит проектировать с оглядкой на rcheevos, не изобретая свой с нуля.
3. Для §11.2 появляется конкретный кандидат в независимые оракулы — stable-retro со
   своими сценариями, при условии допустимых ROM.
4. §NN-01 требует работы, которой нет в SB3: цель Double DQN пишется самостоятельно.
5. Вопрос рантайма обучения на Android (§8.2) ни одним из четырёх источников не закрыт и
   остаётся первым нерешённым инженерным вопросом P1.

## 8. Ограничения этого аудита

- Прочитаны ключевые функции, а не полные кодовые базы.
- Поведение upstream не воспроизводилось (ТЗ §E1 предполагает differential tests — они
  не выполнялись; это честно остаётся незакрытой частью E1).
- Бенчмарков upstream не снималось.
- Три проекта без SHA не рассматривались вовсе.
