## 4. Сверка заявлений ТЗ с фактическим прогоном

### 4.1. ТЗ §2.1 (AGOD PR1) — воспроизведено точно

| Утверждение ТЗ | Факт прогона | Совпало |
|---|---|---|
| структурные кандидаты счётчика и жизней 7/7 | счётчик 7/7, жизни 7/7 | да |
| точный типизированный кандидат счётчика 1/7 | 1/7 | да |

Дополнительно измерено (в ТЗ этого нет):

- жизни, точный типизированный кандидат: **7/7** — то есть по жизням детектор заметно
  сильнее, чем по счёту, и формулировка ТЗ «точный кандидат только 1/7» верна строго
  про счётчик, а не про детектор в целом;
- `fullTypeIdentified`: **0/7** — полный тип не определён ни разу ни по одной переменной;
- счётчик, value-equivalent кандидат: 2/7;
- таймер отклонён 7/7, кадровый счётчик отклонён 7/7 — защита от двух очевидных
  конфаундеров работает.

### 4.2. ТЗ §2.2 (AGOD PR2) — паритет воспроизведён, overhead нет

| Утверждение ТЗ | Факт | Совпало |
|---|---:|---|
| Проверенные записи RAM 32 | 32 | да |
| Writer sites 25 | 25 | да |
| Границы проверки состояния 117 | 117 | да |
| Host active / baseline 1,386× | 1.526× (отдельный прогон), 1.394× (внутри `check.sh`) | **нет, не стабильно** |
| Host detached / baseline 1,201× | 1.525× / 1.285× | **нет, не стабильно** |

Это существенная находка E0: **числа overhead из ТЗ не воспроизводятся устойчиво**.
Разброс между двумя прогонами на одном и том же хосте и коммите — от 1.285× до 1.526×
по detached. Сами по себе значения ТЗ не ошибочны, но это снимки единичных прогонов на
4-vCPU контейнере, а не характеристика механизма. Любое последующее сравнение overhead
обязано опираться на повторные измерения с разбросом, а не на одно число.

### 4.3. ТЗ §2.4 (основной разрыв) — подтверждён измерением

На всех семи контролируемых ROM:

- `verifiedRewards` суммарно **0**;
- `independentConfirmations` суммарно **0**;
- `rewardStatus` = `UNKNOWN` везде;
- `goalPolarity` = `unknown` везде.

То есть разрыв, который ТЗ описывает словами, виден в данных напрямую: конвейер

награды в базе нет вообще. Контракт `UNKNOWN` при этом соблюдается (нулями не подменяется).

## 5. Данные, важные для будущих гейтов

**G6 (≤10% overhead пассивного наблюдения).** Измеренное на хосте отношение стоимости
probe+miner к исполнению ядра: **0.0704–0.1043** (7.0%–10.4%) по семи ROM. Худший ROM
уже на границе целевого порога — и это хост, а не телефон, и это ещё без причинной
проверки и без нейросети. Порог §12.1 следует считать напряжённым, а не запасным.
Это не измерение Android: ни FPS, ни p95 frame time устройства здесь не измерялись.

**Трассировка PR2** даёт p95-отношения 1.25×–1.48× — это на порядок выше 10%, но
относится к ограниченной активной трассировке, а не к постоянному пассивному наблюдению.
Разделение этих двух бюджетов в §13.1 ТЗ корректно и должно сохраняться в отчётности.
