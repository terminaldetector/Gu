## 2. Главные результаты, которые стоит оспорить первыми

### 2.1. Наивное сравнение «действие против нейтрали» систематически ложно

Нажатие кнопки стоит процессорного времени, игровой цикл пропускает vblank и
выполняет меньше итераций — времязависимые байты оказываются **сдвинуты по фазе**.
Измерено буквально: `reset` на 12 кадрах == нейтраль на 11 кадрах.

| | ложных причинных привязок декоев |
|---|---:|
| наивный метод | **101** |
| с допуском на временной сдвиг (траектория-эталон) | **0** |

На 7 картриджах восстановлено: счёт от «положительной» кнопки 7/7, жизни от
«отрицательной» 7/7, меню 7/7, все 8 кнопок по собственному эху, 0 эффектов у
непривязанных кнопок, 0 исключённых стартов. (`logs/causal_report.json`)

### 2.2. Полярность асимметрична, и это ограничение метода

`NEGATIVE` доказуема изнутри эмулятора цепочкой, каждое звено которой наблюдаемо:
действие монотонно уменьшает переменную → переменная упирается в пол → на полу **все
ранее подтверждённые причинные эффекты перестают воспроизводиться**. 7/7.

`POSITIVE` **недоказуема** и заблокирована по построению: 0/7. Изнутри эмулятора
ничто не отличает «счёт» от «счётчика, который просто растёт», а назвать рост
наградой — это ровно запрещённый §1.3 ярлык. **Это самый важный вывод серии и
главный блокер:** без внешнего источника истины автоматически получается только
*избегание*.

Брокер награды: 17/17 негативных кейсов, включая все 8 из §6.3. Пакет `UNKNOWN`
**не содержит ключа `value` вообще** — не 0 и не null; проверено, в том числе через
JSON round-trip.

### 2.3. Тип переменной: выбор вместо списка кандидатов

База не «плохо угадывает» — она **не выбирает**: `fullTypeIdentified` в её стенде —
константа `false`, а точный типизированный кандидат лишь *присутствует в списке* на
1/7. Новый идентификатор обязан выдать один тип.

| | E2 | база |
|---|---:|---:|
| счётчик типизирован верно на наблюдаемо активном span | **7/7** | — |
| из них совпала полная объявленная ширина | **6/7** | 0/7 |
| жизни типизированы точно | **7/7** | — |
| **заявленная кодировка оказалась неверной** | **0** | — |
| знаковость заявлена | **0** | — |
| декой типизирован как игровая переменная | **0** (без нейтрального контроля — **55**) | — |

Три отказа от заявлений, каждый измерен: **знаковость всегда `UNKNOWN`** (беззнаковое
и дополнительное до двух дают одинаковые модульные шаги — изнутри неразличимы);
**байт, который ни разу не переносился, не принадлежит span** (BCD ширины 4 со старта
9 — единственный 1/7, где полная ширина недостижима); **кодировка не определяется,
когда все цифры ≤ 9** (у жизней 0/7 — и это *правильный* ответ, сообщается класс
эквивалентности). (`logs/ram_type_report.json`)

### 2.4. `VERIFIED` больше не приходит фикстурой

Реестр AGOD-08: идентичность старта выводится из ROM + ядро + родительское
сохранение + путь восстановления, поэтому **новый UUID не создаёт нового
доказательства**. Раздел старта — свойство данных (старт из DISCOVERY не может быть
holdout ни для какой цели), повторное использование — свойство пары «цель+старт».

| | результат |
|---|---:|
| цель доведена до `VERIFIED` собственными непересекающимися holdout-доказательствами | **7/7** |
| выплата брокера по такой цели | 7/7, `value = −1` |
| накопитель доведён до `VERIFIED` (реестр как обход к POSITIVE) | **0/7** |
| holdout, пересобранный из стартов discovery | **0/7** |
| обходных путей отклонено по имени | **13/13** |

Среди отклонённых: повышение только из восстановленного кэша («кэш не вправе
повышать гипотезу»), переименованный старт, контрольный эпизод в роли holdout,
просроченные доказательства, импорт состояния от другого ROM.

### 2.5. Нейроагент: учится только когда цепочка выдала подтверждённую награду

Механизм (без эмулятора): аналитические градиенты против центральных конечных
разностей — макс. ошибка **5.4e-11** по каждому параметру; цель Double DQN отличается
от ванильной на расхождении (−1.5197 против −1.2109); детерминизм по сиду; checkpoint
через JSON продолжает **тот же** прогон (< 1e-12).

`DQN.train` в SB3 — ванильный DQN (установлено в E1), поэтому цель Double DQN
**написана, а не портирована**, и обе цели лежат в модуле, чтобы расхождение можно
было показать.

Поведение, 42 прогона (7 картриджей × 6 сидов), заморозка ε=0:

| | штрафуемое действие | потеряно жизней |
|---|---:|---:|
| обученный | **0.000** | **0** |
| необученный (та же инициализация, цель не `VERIFIED`) | 0.508 | 13.3 |
| случайная политика (измерена) | 0.361 | 15.3 |

Устойчивее к выбору сида: **Q(штрафуемое) — минимум из трёх в 42/42**. В контроле
**0 обновлений весов и 0 выплат**. `UNKNOWN`-заявки (426–429 на прогон) **в replay не
кладутся вообще**: отсутствие доказательства не превращается в награду 0.

**И прямое следствие §2.2, видимое в поведении:** среди двух неоштрафованных действий
(ничего не делать / нажимать кнопку, растящую счёт) обученные агенты распределились
**21/21**. За рост счёта награды нет, поэтому агенту безразлично. Он научился не
умирать и ровно ничему больше.

### 2.6. Конвейер на невиданных картриджах (E6/E7)

## 3. Честные оговорки, которые нельзя терять при чтении

1. **Эффективный размер выборки бывает меньше числа прогонов.** Необученная политика
   не зависит от картриджа, и динамика среды агента тоже: 42 прогона E5 дают 6
   независимых траекторий, 21 прогон E7 — 3. Варьируется там конвейер, не агент.
2. **Held-out — не blind-корпус §11.1.** Семена 200…206 из того же генератора.
3. **Исчерпание ресурса ведёт чекер**, трек читается по найденному адресу;
   автономного поиска «что считать событием» нет.
4. **Задача проста.** «Не нажимай штрафуемую кнопку» — короткий ответ; результат
   доказывает корректность механизма, а не способность решать игры.
5. **Отделение эха ввода от игрового состояния** решено через «сохраняется после
   отпускания» (это сузило ограничение C3.3 из E4, где область подавалась извне). Эхо
   с защёлкой так не отделится.
6. **Числа overhead из ТЗ §2.2 не воспроизводятся устойчиво**: два прогона на одном
   коммите дали 1.285×–1.526× против заявленных 1.386×/1.201×. Это характеристика
   единичных снимков, а не механизма.
7. **G6 уже напряжён на базе**: probe/core на хосте 7.0%–10.4% против порога ≤10% —
   ещё до причинной проверки и нейросети. Конвейер при этом дорогой: на картридж 8
   причинных зондов + нейтральный прогон + типизация по маскам + три партиции с
   исчерпанием.

## 4. Четыре ошибки, которые я поймал сам (и как)

1. **E3.** Собственный наивный зонд привязал `frameCounter`/`timer`/`noise` к маскам
   4/64/128 на seed 2. Диагностировано измерением (reset на 12 кадрах == нейтраль на
   11), исправлено контролем временного сдвига. Отсюда и цифра 101.
2. **E4.** Критерий «исчезли все подтверждённые эффекты» неверен: картридж пишет эхо
   кнопки и «после смерти». Введена явная область адресов, ограничение
   задокументировано, а не спрятано.
3. **AGOD-08.** `promote()` возвращал сразу три взаимоисключающих блокера про holdout,
   когда holdout не было вовсе, и рапортовал отсутствие калибровки у противоречивых и
   просроченных гипотез, где `assess()` коротко замыкается. Два из трёх — ложные
   утверждения о несуществующих данных. Исправлено.
4. **E7.** Первый прогон агентной части дал идеальные `0.000` — и это ничего не
   значило: последнее действие конвейера — исчерпание ресурса, то есть машину он
   отдаёт **мёртвой**, и агент стартовал с нулём жизней. Величина всех заявок нулевая,
   выплат 0, обновлений весов 0, «избегание» — необученный argmax в замороженном мире.
   Поймало утверждение `runsWithoutWeightUpdates === 0`; добавлено `paidClaims > 0` на
   каждый прогон. Числа конвейера не затронуты: дефект был **после** фиксации ответа.

Плюс одно переименование по существу: метрика `effectMaskCorrect` считала, совпала ли
«эффектная» маска с кнопкой счёта. Конвейеру нужен **любой** сохраняющийся
возрастающий эффект как область игровых эффектов, и счётчик уровня годится не хуже;
«найти счёт» он не обещает. Переименовано в `effectMaskIsScoreButton` и переведено в
информационные: 3/7 и 2/7 — наблюдение, а не провал.

## 6. Решения, которые нужны от тебя

1. **Чем закрывать `POSITIVE`?** Это блокер №1: без внешней истины агент умеет только
   избегать. Варианты, как я их вижу: (а) независимый оракул §11.2 на рукописных
   сценариях Stable-Retro — годится как оракул, но не как путь обнаружения;
   (б) человеческая разметка на этапе калибровки; (в) holdout-подтверждение с
   участием человека. Какой из них считать штатным?
2. **Blind-корпус §11.1 — из чего?** Коммерческие ROM в репозиторий нельзя. Homebrew
   с совместимой лицензией? Второй независимый генератор, написанный не мной? Кто его
   пишет?
3. **Где живёт обнаружение?** Конвейер дорогой, а G6 напряжён уже на базе. Обнаружение
   — отдельный офлайн-сеанс (не во время игры), или оно обязано влезть в живой бюджет?
4. **FDB и MLP.** В E5 голова — обычный MLP, `Engine`/`FdbLearning` я намеренно не
   трогал. ТЗ требует нейроагента, исследовательская цель проекта — FDB. Нужно явное
   решение: подменять голову LIF-субстратом (и тогда где — `Wexo`, обучаемая проекция?)
   или держать их раздельно до закрытия G5.
5. **TTL доказательства** — 48 часов взяты по умолчанию и **не измерены**. Какой
   горизонт устаревания считать правильным?
6. Нужен ли **сравнительный baseline** (SB3 и т.п.) как отдельный эксперимент, или
   упоминания ванильной цели как контрпримера достаточно?

## 7. Воспроизведение

Из корня репозитория на ветке `research/agod-neural-e0-e1`:

```sh
pip install -r tools/requirements.txt
AGOD_RAM_REPORT=logs/ram_type_report.json      node tools/agod_ram_check.cjs
AGOD_CAUSAL_REPORT=logs/causal_report.json     node tools/agod_causal_check.cjs
AGOD_REWARD_REPORT=logs/reward_report.json     node tools/agod_reward_check.cjs
AGOD_EVIDENCE_REPORT=logs/evidence_report.json node tools/agod_evidence_check.cjs
AGOD_DQN_REPORT=logs/dqn_report.json           node tools/agod_dqn_check.cjs
AGOD_PIPELINE_REPORT=logs/pipeline_report.json node tools/agod_pipeline_check.cjs
```

Все завершаются кодом 0 и печатают итоговый JSON последней строкой. Последние две —
десятки минут. **Список held-out-семян (200…206) менять нельзя: это условие оценки,
а не параметр.** Подробности и ограничения окружения — в `reproduction.md`,
`known_limitations.md` (разделы A–D, C2–C7), `environment.json`, `sha256sums.txt`.
