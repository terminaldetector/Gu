# Два журнала Android · GU 2.1.4 → 2.1.5

23 октября 2026 года. Оба предоставленных архива проверены штатным
`tools/inspect_diagnostics.py`; контрольные суммы файлов и событий совпали.
Сырые ZIP, идентификаторы устройства/процессов/игр и содержимое записей
в репозиторий не включены. [Агрегаты](device-metrics.json) обезличены.

Оба архива получены от одной сборки 2.1.4/code38, Android 16 / WebView 143.
Первый содержит около 15 минут 40 секунд. Второй содержит хвост прежнего
процесса и два следующих запуска; между ними есть часы без записи.
Он **не является непрерывным восьмичасовым нагрузочным тестом**. Старые
сегменты вытеснены кольцевым журналом; внутри сохранённых последовательностей
пропусков нет. Максимальное время game save второго архива включает фон и
возврат приложения, поэтому не измеряет чистую скорость диска.

### REC и меню

Второй архив начинается после первоначального сбоя архива показа. События
4322 и 4348 прежнего процесса содержат «Хранилище показа не ответило».
При повторном открытии панели очередь FDB-примеров уже равна нулю.
Ручной режим и отключение сети остаются доступны: бесконечная блокировка
всего приложения журналом не подтверждается.

Причина повторного отказа воспроизведена на настоящем NES с явной native RPC
фикстурой: `Writer.failed` остаётся историей последней записи, а safe-pause
повторно проверяет его даже в следующем режиме подсказок без новых действий.
Первоначальную причину таймаута имеющийся хвост не раскрывает: успешные ACK
архива раньше отдельно не журналировались.

В 2.1.5 результат `humanTeaching.stop()` относится к конкретной попытке
записи. Новая/ожидающая ошибка архива остаётся явной; STOP не объявляет
такую запись сохранённой. Прежний закрытый архив не блокирует последующую
паузу без новых примеров или другую игру. Ошибка сохраняется в истории и
показывается в панели как предупреждение. Данные и ошибка не стираются
ради успешного перехода.

### Фон и запоздалый запрос

Для `pause-14` во втором архиве native-запрос — событие 4506. Таймаут 4514
зарегистрирован через 36,63 с: даже 15-секундный обработчик был задержан ОС.
JavaScript начал сохранение только после возврата в foreground, событие 4519.
После этого game save занял 226,9 мс, learned save также сообщил успех;
поздний ACK отклонён. Это задержка запуска фоновой работы, **не доказательство
медленной IndexedDB или повреждения сохранения**.

В 2.1.5 JavaScript до паузы проверяет действительность native lifecycle-token.
Просроченный/заменённый запрос после возврата больше не приостанавливает
возобновлённую игру и не создаёт сохранение для нового ROM. Отмена явно
журналируется, успешный ACK не выдумывается. Выполнение JavaScript при
замороженном WebView этим исправлением не гарантируется; timeout остаётся.

В первом архиве stale ACK после быстрого возврата ожидаем: foreground
наступил через 180 мс, сохранение завершилось через 1,56 с. Само слово
`stale` не доказывает потерю данных.

### Обучение и неизвестный результат

Первый архив содержит 14 уникальных episode-id: 13 закрытых и один открытый.
Второй — 40 закрытых. Файлы `.open`/`.closed` одной записи не считаются
независимыми эпизодами. Вложения между архивами также пересекаются;
их нельзя просто складывать в независимую выборку.

У всех закрытых записей outcome/confidence неизвестны, knownFeedback=0,
independent=false. У первого архива 477 unknown-feedback и 172 вмешательства,
у второго — 2630 и 400. FDB digest меняется, но это **не доказательство
приобретённого игрового улучшения**. Экспорт не содержит frozen proofs.

Найдена ошибка представления: интерфейс писал «0.00; успех false» при
неизвестном исходе. Native FDB при этом не получал выдуманную награду.
В 2.1.5 показаны «награда неизвестна» и «результат неизвестен»; измеренный
ноль, частичные данные и подтверждённые win/death различаются. График не
соединяет неизвестные результаты с нулевой линией. Прежние числовые поля
сохранены для совместимости; алгоритм пластичности не изменён.

## Производительность Male CNS

Выбраны только periodic-окна Sega, realtime, playing=true, hidden=false,
длительность не меньше 2 с. p50/p95 ниже — медианы перцентилей отдельных
окон, **не глобальные перцентили всех запросов**. Условия и игры различаются;
это наблюдение, не контролируемый A/B.

| Архив / режим | Окон / samples | Медиана FPS | p50 sample, мс | Ответов/с | p50 сохранения FDB, мс |
|---|---:|---:|---:|---:|---:|
| Первый · train ×1 | 129 / 1028 | 60,00 | 378,35 | 1,61 | 271,67 |
| Второй · train ×1 | 12 / 79 | 60,03 | 488,41 | 1,41 | 196,19 |
| Второй · train ×2 | 196 / 1606 | 120,02 | 379,01 | 1,64 | 270,27 |

При ×2 минимум FPS в этих окнах — 115,38. Эмуляция и частота решений агента
измеряются отдельно. В первом архиве медиана worker queue p50 — 58,02 мс,
во втором при ×2 — 216,00 мс; WebView apply — около 1,1–1,2 мс.

Измеренный `feedback.saveMs` относится к mutable Current: после unknown-boundary
он сохраняется до ACK. В первом срезе 1028 sample и 513 save, во втором ×2 —
1606 и 804. Сам feedback занимает около 0,01–0,02 мс, сборка состояния —
около 0,8 мс. `LayerSetStore` читает/проверяет/сериализует checkpoint и
атомарно записывает Recovery и Current с `fsync`. `LearnedRoles.checkpoint`
в это измерение не входит. Разные стадии нельзя просто складывать.

Сохранения unknown нельзя просто пропустить: boundary очищает eligibility,
решения меняют RNG, действует контракт durable Current до ACK. Ускорение
пока **не заявляется**. Следующий замер должен разделить read/encode/две
записи и размеры checkpoint; затем можно проверить устранение повторной
обработки уже проверенного поколения с сохранением прежнего Recovery.

Native PSS достигает 655,4 МиБ в первом архиве и 567,0 МиБ во втором;
Java used — 367,0 и 323,8 МиБ при heap limit 512 МиБ. Это память native
процесса **без отдельного WebView renderer**. Температура батареи достигает
44,9 °C; эти датчики не доказывают thermal throttling или калиброванный расход
энергии. Доказательств утечки памяти из этих снимков нет.

## Память, восстановление и пределы проверки

Male CNS сначала отклонён безопасным бюджетом памяти, затем загружен при
повторной попытке; прежний граф сохранён. Android exit history содержит
`REASON_LOW_MEMORY`, status 9, background importance. Java OOM не записан.
В старом журнале нет имени/PID завершённого процесса, поэтому строго
сопоставить причину с главным процессом или renderer нельзя. В 2.1.5 эти
поля добавлены. Для RPC архива добавлены operation/token, worker queue,
storage/total timing и успех native-операции до отправки WebView ACK;
сами действия/веса в эти события не попадают.

Последний процесс заканчивается `game.load.begin` и экспортом без
`game.load.end`: успешное восстановление этим хвостом не подтверждается.
Звук выключен. Геометрии DOM/CSS в журнале нет: исправность портретной
раскладки нельзя доказать только по viewport. Нужна физическая проверка
сохранения при фоне/остановке процесса и продолжения на телефоне.

Результаты регрессий и Android build/lint приведены в `validation.json`
после завершения прогона. Тесты протокола используют явно обозначенные
native-ответы, а не доказывают обучение полного коннектома.
