# LFM: быстрое принятие решений — ход работ (Track A–D)

Все числа ниже — **хост** (x86_64, 4 vCPU), не Android. На телефоне ничего не
измерено: физическое устройство — DEVICE-PENDING; замер на нём делается кнопкой
«Диагностика → Быстрый контур» (Track B) и инструментами `research/lfm_fast/` после
переноса графа.

## Track A. Визуальные признаки LFM2.5-VL-450M без языковой модели

### 1. Реальный инференс без генерации текста

`research/lfm_fast/lfm_fast_vision.py` — отдельный граф из официальных весов:
кадр → патчи 16×16 (без процессора и без паддинга до 1024) → SigLIP2 (12 слоёв) →
post-norm → проектор (pixel-unshuffle 2×2, MLP) → признаки `proj` (64 × 1024 для
NES). Ранние выходы: те же токены изображения между `<|image_start|>` и
`<|image_end|>` через первые слои LFM2 — `lm2` (после слоёв 0–1, conv/conv) и `lm4`
(после 0–3, conv/conv/attention/conv). Нет таблицы эмбеддингов (оставлены две строки
спецтокенов), нет LM head, нет проекции в словарь, нет генерации, нет KV-кэша.
Позиционные таблицы для фиксированной сетки консоли — константы.

Сверка с transformers на одном кадре: `proj` max |Δ| = 0.0011 при среднем |x| = 3.62
(относительная ошибка на токен 1.5·10⁻⁵); `lm2`/`lm4` совпадают с
`hidden_states[2]`/`[4]` точно. (Первая версия давала расхождение 3.46: процессор
масштабирует кадр в uint8 — исправлено, сверка это и поймала.)

### 2. Скорость вариантов (torch fp32, мс на кадр NES, p50 / p95)

| вариант | токены | параметры | 1 поток | 2 потока | 4 потока |
|---|---|---|---|---|---|
| `proj` (без LM) | 64 | 94.0 M | 393 / 423 | 210 / 222 | 116 / 137 |
| `lm2` | 64 | 130.7 M | 415 / 433 | 236 / 256 | 139 / 171 |
| `lm4` | 64 | 166.4 M | 481 / 520 | 264 / 279 | 156 / 202 |
| `proj`, 6 слоёв зрения | 64 | 51.5 M | 191 / 220 | 107 / 115 | 64 / 79 |
| `proj`, 12 токенов (сетка 6×8) | 12 | 94.0 M | 110 / 115 | 59 / 63 | 38 / 46 |
| `proj`, 12 токенов, 6 слоёв | 12 | 51.5 M | 58 / 67 | 31 / 37 | 17 / 22 |

Стоимость определяет энкодер зрения; ранние выходы LM добавляют 23 мс (`lm2`) и
40 мс (`lm4`) к 116 мс на 4 потоках. Полное зрение на каждом решении при 30 Гц
(33 мс) невозможно ни в одном варианте с 64 токенами — отсюда архитектура:
медленный асинхронный путь LFM + быстрый путь движения на каждом кадре (Track C).

### 6. Отдельный граф с минимальными операторами (ONNX, onnxruntime CPU)

`research/lfm_fast/lfm_onnx_graph.py`: экспорт (torch.export → ONNX), сверка с
torch (max |Δ| ≤ 0.0042), int8 (динамическое квантование весов MatMul/Gemm).
Память — пик `VmHWM` **нового процесса**, в котором только onnxruntime и файл графа
(базовый уровень процесса 47 МиБ). Размер файла приведён отдельно и памятью не
является.

| граф | файл fp32 / int8 | пик памяти fp32 / int8 | fp32 p50 (1 / 4 потока) | int8 p50 (1 / 4 потока) | косинус int8↔fp32 на реальных кадрах (токен / пул) |
|---|---|---|---|---|---|
| `proj` | 360 / 91 МиБ | 455 / 187 МиБ | 343 / 113 мс | 81 / 35 мс | 0.78 / 0.94 |
| `lm2` | 500 / 127 МиБ | 596 / 224 МиБ | 384 / 135 мс | 90 / 41 мс | 0.79 / 0.94 |
| `lm4` | 636 / 161 МиБ | 734 / 259 МиБ | 456 / 142 мс | 101 / 52 мс | 0.79 / 0.94 |
| `proj`, 6 слоёв | 198 / 50 МиБ | 291 / 144 МиБ | 181 / 53 мс | 44 / 23 мс | 0.92 / 0.96 |

Для сравнения: процесс с полным чекпойнтом transformers — 3.3 ГиБ RSS. Отдельный
визуальный граф укладывается в бюджет 2–3 ГБ с большим запасом.

Динамический int8 заметно искажает потокенные признаки (косинус 0.78–0.79 на
реальных кадрах Contra). По правилу «сначала доказать выигрыш качества управления,
потом квантовать» int8 не принимается до сравнения качества управления на тех же
траекториях; это отдельный пункт Track D.

Числа: `docs/architecture-reset/lfm_fast_vision_bench.json`.
