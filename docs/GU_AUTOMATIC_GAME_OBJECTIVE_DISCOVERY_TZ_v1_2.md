# GU / FDBP: Automatic Game Objective Discovery & Goal Induction (AGOD v1.2)

**Техническое задание для Codex · редакция v1.2 от 23.10.2026**
**Приоритет:** P0 для автономного обучения; внедрение по проверяемым этапам
**Репозиторий:** `terminaldetector/Gu`
**Рабочая отправная точка:** `feature/autonomous-learning-emulator` (проверить фактический HEAD и незакоммиченные изменения до начала).
**Исследовательское основание:** `docs/FDB_RESEARCH_HANDOFF_AB_A2_A3_RU.md`
**Цель:** автономно обнаруживать кандидатов на игровые события, проверять их достоверность и, когда это обоснованно, формировать награду для существующей FDB-пластичности. Без ручного ввода RAM-адресов, ручных оценок +1/−1 и назначения контрольных слоёв в основном пользовательском режиме. **Масштабирование:** разработка правила награды вручную для каждого ROM не является допустимой архитектурой продукта.

## Целевое поведение обычного пользователя (дополнение v1.1, обязательно)

**Потребитель не настраивает награду.** Загрузка поддерживаемого ROM должна автоматически запускать локальную процедуру обнаружения игрового смысла и кэширования профиля. Не спрашивать RAM-адрес, знаки награды, число жизней, контрольный Save State, «победа/поражение» или ручные +1/−1. Эти действия допускаются только в скрытой лабораторной диагностике; отсутствие ручной настройки не препятствует обычной игре.

Пользовательский сценарий: `Open ROM → Game ready → Discovering goals → Validating game events → Autonomous learning enabled if verified`. **Нельзя требовать ручного ROM-by-ROM onboarding даже при первой загрузке.** Фаза исследования выполняется с ограниченным вычислительным бюджетом. Игровой runtime не блокируется и не ждёт завершения анализа. Если надёжная внешняя цель не обнаружена, агент может исследовать игру в режиме без подтверждённой игровой награды; **прогресс самообучения и Best не заявлять**. При последующих запусках применять локально сохранённый профиль только после проверки ROM SHA256, версии ядра, mapper/bank, схемы детектора и evidence freshness.

### Обязательное расширение: `GameGoalInduction` (не только RAM EventDiscovery)

Обнаружение изменения памяти ≠ обнаружение цели. Помимо `EventHypothesis` ввести отдельные, версионированные:

- `GamePhase`: `boot|menu|playing|paused|death|respawn|transition|complete|unknown`, с доказательствами из CPU/RAM и изображения; при неуверенности `unknown`.
- `GoalHypothesis`: предикат события, его **полярность** (`positive|negative|neutral|unknown`), значимость (`primary|auxiliary|unknown`), временной горизонт, связи с другими событиями (например `score↑ ↔ enemyDefeated`, `lives↓ ↔ respawn`, `stage↑ ↔ sceneTransition`), альтернативы, признаки ложного толкования.
- `GoalEvidence`: независимые игровые старты, события до/после, влияние собственных и нейтральных действий, повторяемость, противоречия, полярность, доверие; отдельные discovery/calibration/holdout источники.
- `GameObjectiveProfile`: `(ROM hash, platform, mapper/core revision, detector revision)` + проверенные игровые фазы, события, голевые предикаты, полярности, reward scales, списки исключений, происхождение и статус (`discovering|provisional|verified|invalidated`). Профиль **не содержит приобретённые нейронные веса**, не является Learned Layer и не переносится между ROM по совпадению заголовка.

**Как выводить полярность без человека:** сочетать отношения в графе событий, переходы игровых фаз, изменения наблюдаемого изображения, происхождение из ветвлений кода, и сравнение альтернативных действий из одинакового состояния. Например, `lives--` вместе с `death→respawn` поддерживает негативную полярность, а `stage++` вместе с `sceneTransition` поддерживает прогресс. `score++` сам по себе не достаточен, а `counter++` без контекста не имеет знака. Результат может оставаться неопределённым.

Извлечение из машинного кода имеет целью **построить карту причинных зависимостей**, а не «прочесть заложенную разработчиком награду»: NES PRG ROM содержит машинные инструкции процессора 6502 и данные, а не стандартное поле fitness/reward. Для других платформ необходимы отдельные адаптеры декодирования, но целевой протокол `GameGoalInduction → GameObjectiveProfile → RewardEvidence` должен оставаться общим.

### Автоматический cold start без ручного указания награды

1. Встроенный low-overhead observer регистрирует изменения, динамические игровые фазы и ограниченные кандидаты на переменные.
2. В discovery-режиме запускать **ограниченное, детерминированно воспроизводимое** исследование действиями агента: сбалансированные допустимые маски, отсутствие неподтверждённых внешних наград, ограничение бюджетов, отдельная пометка `exploration_only`.
3. Для перспективных кандидатов включать bounded CPU writer tracing, после чего **по возможности** проверять альтернативные действия в изолированных прогонах из Save State. Такие прогоны не должны изменять игру пользователя, Current/Best или нейронные параметры, а должны учитывать реальную производительность Android.
4. Автоматически строить, проверять и ранжировать `GoalHypothesis`, в том числе отрицательные свидетельства и смену смысла переменной после перехода уровня/меню.
5. Только прошедшие заранее фиксированный confidence gate `GoalHypothesis` переводить в `GameObjectiveProfile=verified`, затем в `RewardEvidence` для существующего FDB bridge. Не выдавать за игровое обучение новизну RAM или исследования состояния.
6. Мониторить противоречия во время последующей игры; профиль отзывать при нарушении инвариантов, изменении контекста либо устойчивом росте ложных событий. В этом случае вернуться к `discovering`, блокируя неверную награду, но **не сбрасывать приобретённую модель автоматически**.

Вычислительные лимиты (время tracing, memory, action probes, write events, CPU/battery) и правила переходов `discovering → verified → invalidated` должны быть явными, конфигурируемыми на уровне движка и проверены тестами. Не давать пользователю конфигурационный экран для каждого ROM.

### Дополнительные критерии приёмки для потребительской автономности

- Для нового поддерживаемого контрольного NES ROM с неизвестными детектору правилами система обнаруживает **тип, знак и условие** минимум одного положительного и одного отрицательного события **без ручных полей или подсказок разработчика**, документируя latency до первой verified-награды.
- На тестовых ROM со счётчиком кадров, таймером, high score и ложными переходами система не записывает эти значения в `positive reward` без повторяемых причинных доказательств.
- На нескольких лицензированно доступных, ранее не использовавшихся в разработке ROM проводить blind-проверку: доля обнаруженных целей, ложноположительные/ложноотрицательные события, калибровка confidence, время до надёжного профиля, фактическое изменение FDB и эффективность обучения против frozen/random. Синтетический ROM сам по себе **не означает** универсальную пригодность к реальным играм.
- Если цель не выводится из наблюдений, GU продолжает играть и исследовать, сообщает `Цель не подтверждена`, сохраняет наблюдения и не заявляет об успешной автономной награде. Запрещено незаметно падать обратно в ручную оценку.
- После повторной загрузки ROM подтверждённый локальный профиль восстанавливается без переоткрытия лаборатории, а его несовместимость обнаруживается и приводит к безопасному повторному discovery.

## Новый материал v1.2: аудит игровых технодемо и требование массовой автоматизации

### Почему это обязательная часть архитектуры, а не удобство интерфейса

Библиотека поддерживаемых ROM состоит из большого числа независимых программ, у которых различаются правила, карты памяти, способы кодирования чисел, мапперы, игровые фазы, таблицы данных и программная логика. **Ручное назначение функции награды для каждой игры недопустимо как основной способ эксплуатации GU.** Оно превращает заявленную автономность в разработку отдельного RL-окружения для каждого ROM, переносит работу с разработчика на пользователя и не масштабируется по каталогу.

Уточнение терминологии: NES-ROM содержит преимущественно **машинный код 6502-совместимого CPU и данные**, а не универсальный платформонезависимый «байткод». Другие системы используют другие CPU/форматы. Полное статическое дизассемблирование всего ROM не является необходимым или достаточным методом получения семантики награды. Вместо этого нужен **запускаемый анализ исполнения с селективной инструментализацией**, который извлекает только релевантные участки и проверяет гипотезы на поведении игры. Размер ROM сам по себе не делает допустимым безграничное полное трассирование.

**Продуктовый invariant:** `открыть ROM → играть → автоматическое discovery → VERIFIED GameObjectiveProfile → обучение FDB`; ни на одном штатном шаге пользователь не обязан выбирать адрес, выставлять оценку действия, размечать train/control или писать скрипт для своего картриджа. Если цель не установлена, честное `UNKNOWN` вместо ложного обещания автономного обучения.

Проверка нескольких проектов не доказывает отсутствие других подходов; утверждение относится только к перечисленным исходникам.

### Архитектурный принцип масштаба: один анализатор, множество ROM

Разделить реализацию по независимым уровням:

1. **`CoreProbeAdapter` — специфичен для платформы, не для игры.** Унифицированные операции: наблюдение RAM, CPU writer site, PC/mapper/bank provenance если доступно, управление watchpoints, безопасный Save State snapshot, isolated replay, capability flags и лимиты. На первом этапе — NES; будущие Sega/GB/SNES потребуют собственные адаптеры, а не новые правила награды в UI.
2. **`GameStateSemantics` — общий механизм классификации событий.** Строит кандидатов `score/lives/death/level/transition/unknown` по цепочкам состояний, контексту фаз, передаче управления и причинным экспериментам. Никаких таблиц `if (romTitle === ...)` как основного алгоритма.
3. **`ObjectiveProfileCompiler` — компиляция обнаруженного смысла в дешёвые проверяемые правила.** После discovery сохранённый `GameObjectiveProfile` содержит компактные RAM watchpoints/фазовые предикаты, evidence и условия аннулирования. В обычном игровом режиме повторный полный анализ кода не нужен.
4. **`GoalEvidenceRegistry` — происхождение, противоречия и оценка ошибок.** Учитывает скрытые тестовые ROM, независимые старты, false positives, confounds и confidence. Никакого переноса сырого RAM-адреса между ROM по похожему имени.
5. **`RewardSynthesizer → существующий FDB` — только VERIFIED.** Определение игровых целей существует отдельно от нейронной политики и не даёт ей прямой доступ к трассам кода как «читерским» признакам.

Для одного ROM жизненный цикл должен иметь конечные состояния:

`UNSEEN → DISCOVERING → CANDIDATES → VALIDATING → VERIFIED → MONITORING`, с переходами `VALIDATING/MONITORING → UNSUPPORTED|UNKNOWN|INVALIDATED` по измеренным причинам. Повторный запуск применяет VERIFIED профиль только при совпадении ROM SHA256, платформы, mapper, core revision, schema и выполнении cheap sanity checks. При изменении любого из них инициировать безопасную повторную валидацию, а не слепо применять старый профиль.

**Селективность:** сначала дешёвые RAM-diff, изменение экрана и границы игры; затем ранжирование потенциально значимых переменных; затем writer-PC trace лишь для top-K кандидатов и коротких временных окон; затем изолированные action/no-op/alternative-прогоны только для оставшихся неопределённостей. Не сканировать весь ROM инструкцию за инструкцией при каждом игровом кадре. Экономия вычислений должна быть измерена на Android, а не только описана.

**Возможная будущая оптимизация:** переиспользовать *абстрактные детекторы* событий и статистические априорные признаки между играми одной платформы, но не копировать конкретные RAM-адреса, знаки наград или необоснованную уверенность. Проверка на новой игре всегда самостоятельна.

### Проблема неопределённой семантики и холодного старта

Программная трасса определяет, *кто изменил память*, но не отвечает, *зачем такое изменение хорошо*. Существует принципиальная неоднозначность: при одинаковых наблюдениях `counter++` может быть счётом, временем, убытком или частью анимации. Поэтому для неизвестного ROM discovery может **не суметь определить знак награды**, и это не баг, который разрешается случайным `+1`.

Допустимые средства уменьшить неоднозначность: фазовые переходы, прекращение жизни/возврат к старту, повторяемые зависимости от действия, сопоставление множества переменных, контролируемое сравнение из одного Save State, проверка на новых независимых стартах. На реальной игре нельзя считать «score вырос» доказательством победы без контекста и противодействия reward hacking.

**Cold-start без внешней цели:** ограниченное исследование (exploration) без утверждений о полезном FDB-обучении; intrinsic novelty остаётся самостоятельным диагностическим показателем, пока не доказано, что её включение безопасно. Пользователь при этом может продолжать игру независимо от успеха анализатора. Никакого скрытого возврата к `manual` для обычного потребителя.

### Результат этой редакции и критерии масштабируемости

Дополнительно к последующим AGOD-0…AGOD-4 тестам Codex обязан:

- Создать один `CoreProbeAdapter`/контракт capabilities, не встраивать ROM-specific `reward()` в `lab.js`.
- На собственных контролируемых NES-ROM **не передавать внутренние oracle-метки алгоритму**: эталонная семантика доступна только тестовому проверяющему после прохождения discovery.
- Использовать несколько разных скрытых тестовых сценариев с положительными и отрицательными событиями, таймерами, меню, high score, reset, изменением bank. Хотя бы часть ROM/сценариев не должна быть известна детектору при настройке правил.
- Измерять по каждому ROM: latency `Open→first VERIFIED`, процент ROM с VERIFIED, полноту/точность обнаружения событий, число ложных положительных reward, долю времени `UNKNOWN`, объём CPU trace, frame-time p95/p99, энергию и память устройства, использование кэша после повторной загрузки.
- Отдельно выводить результаты `unit/host controlled ROM/held-out ROM/Android device`. Устройство без измерений получает `DEVICE-PENDING`, а не фиктивный PASS. Сравнивать не только количество найденных адресов, но **правильность знака/смысла событий и реальное влияние на FDB** против frozen/random.
- После завершения discovery штатная эмуляция должна использовать **компактные наблюдатели событий**, без постоянного полного CPU tracing. При превышении бюджета выключать discovery без остановки эмулятора и без генерации фиктивных reward.
- Не обещать поддержку всех ROM. Отчитываться о доле уверенно разобранных игр, ограничениях mapper и случаях `UNKNOWN`, не маскировать отсутствие цели прогрессом весов.


## 0. Обязательные границы

1. **Не строить второй агент обучения.** Подключаться к действующим `autonomous-episodes.js`, `EpisodeHistory`, `CurriculumStore`, `EvaluationArchive`, `LearnedRoles`, `BestPromotionGate`, `fdb-feedback.js` и существующему `FdbLearning.feedback()`.
2. **Не считать произвольное изменение памяти успехом.** Отсутствие подтверждения означает `UNKNOWN`, а не `reward=0`, `win=false` или «поражение».
3. **Не делать вид, что у машинного кода есть универсальный признак победы.** ROM NES содержит инструкции 6502, данные и таблицы, часто с банковым переключением. Дизассемблирование и трассировка дают происхождение состояния, но не семантику игровой цели без проверки.
4. **Сначала NES, контракт — для нескольких архитектур.** Sega/GB/SNES оставить за `CoreProbeAdapter`/capabilities, без вмешательства в их WASM/эмуляторные ядра на этом этапе. Не хардкодить NES-адреса в общих классах.
5. **Только offline/on-device.** Никакой отправки ROM, кадров, памяти или трасс на сервер; никакой обязательной облачной LLM. Не включать коммерческие ROM в тестовые артефакты.
6. **Сохранять контракт эмулятора и модели.** W₀ неизменен; ΔW/Wexo/пороги и отдельные Current/Best/Recovery сохраняются как сейчас. Не модифицировать GPU-ядро или алгоритм FDB ради обнаружения целей.
7. **Не объявлять готовность по синтетическому демо.** Результаты на инструментированном тестовом ROM и на пользовательских играх разделять.

## 2. Контур и публичные контракты

```
NES frame / CPU execution
         │
         ├── RAM & game-state snapshots ─────────────┐
         └── bounded CPU write trace / bank context  │
                                                     ▼
                                              State Candidate Miner
                                                     │
                                              Event Hypotheses
                                                     │
                                         Replay / Causal Validator
                                                     │
                                    Evidence Registry + Confidence Gate
                                                     │
                    ┌────────────────────────────────┴───────────────────┐
                    ▼                                                    ▼
             VERIFIED_EVENT                                         UNKNOWN / CANDIDATE
                    │                                                    │
              RewardSynthesizer                                  diagnostics only
                    │                                                    │
              FDB feedback                                       no FDB mutation
                    │
           EpisodeHistory / Frozen Evaluation
                    │
             Existing BestPromotionGate
```

Ввести минимальные, версионированные структуры данных:

- `GameObservation`: `context` (platform, ROM SHA256, core revision, run/episode/start, frame, generation), RAM snapshot или bounded delta, input mask, emulator-state fingerprint; без лишних полных копий кадров.
- `MemoryWriteTrace`: frame/cycle, CPU PC, mapped PRG bank/offset **если известны**, address, old/new value, write origin (`cpu`, `dma`, `unknown`), trace coverage/overflow flag.
- `EventHypothesis`: адреса/ширины/типы, преобразование значения, предполагаемая роль (`score`, `lives`, `level`, `terminal`, `progress`, `unknown`), provenance, контекст обнаружения, альтернативные объяснения.
- `EventEvidence`: `eventId`, наблюдаемые переходы, повторяемость, контроли, проверка независимости, confidence/uncertainty, reasons for rejection, detector version.
- `RewardEvidence`: `status=UNKNOWN|OBSERVED|VERIFIED|REJECTED`, `eventId`, `episodeId`, `actionWindow`, `reward` **только при VERIFIED/обоснованно OBSERVED по установленному контракту**, `confidence`, `source`, `traceId`, `terminal`, `validUntil`, `contextHash`.

Не использовать JSON из WebView как неограниченный доверенный источник: валидация размеров, значений, контекста, сроков действия и sequence обязана существовать по обе стороны JS/native bridge.

## 3. Stage AGOD-0: регистрация наблюдений и RAM-кандидатов

Реализовать лёгкое обнаружение без CPU-трассировки:

1. Снимать RAM-состояния на заданной частоте/границах нейронных действий; вычислять bounded diff без постоянной полной сериализации.
2. Исключать зеркала RAM, некорректные адреса, заведомо монотонные счётчики кадров, таймеры, шумные/нестабильные поля и высокоэнтропийные значения как **предварительные** артефакты, не универсальные исключения.
3. Строить кандидаты на 1–4-байтовые unsigned/signed/BCD счётчики, little/big endian, с проверкой переполнений, циклов, сбросов и связанных переменных.
4. Обнаруживать переходы, потенциально связанные с потерей жизни, сменой уровня, экраном завершения, увеличением счёта, но маркировать их `CANDIDATE`.
5. Фиксировать корреляции с изменением экрана и применёнными действиями, учитывая возможную задержку между кнопкой и следствием.
6. Повторные наблюдения от одного и того же прохождения **не считать независимыми подтверждениями**.

Результат: ранжированный реестр гипотез с негативными примерами и воспроизводимой записью происхождения, без автоматического FDB reward.

## 4. Stage AGOD-1: NES execution tracing / машинный код

Инструментировать NES 6502 **ограниченно и воспроизводимо**:

- Снимать PC и записи на CPU memory bus вместе с frame/cycle, адресом и значениями до/после.
- Различать базовую 2 KiB RAM и её зеркала; не принимать PPU/APU/I/O/mapper записи за игровые переменные в RAM.
- Для PRG-ROM учитывать mapper, bank switching, адресное пространство и доступность сопоставления `PC→ROM offset`; при неоднозначности сохранять `unknown`, не выдавать ложный адрес инструкции.
- Не путать выполнение инструкции, вызвавшей запись, с логической функцией игры: PC/write-site служит доказательством происхождения, не автоматическим ярлыком `VICTORY`.
- Допустить watchpoints по отобранным адресам, трассировку ограниченных окон и bounded ring buffer с отчётом о пропущенных событиях.
- Минимизировать overhead: instrumented research/discovery mode и fast-path без полного трассирования во время обычной игры. Никогда не писать полный поток инструкций в постоянный журнал по умолчанию.
- Использовать контролируемый, проверяемый исходный код NES-ядра/публичный adapter; не патчить вручную `jsnes.min.js` без воспроизводимой сборки и регрессионного сравнения поведения.

Критерий: на специально подготовленном NES ROM точно установлен writer-PC/bank для известных счётчиков; при неподдержанном mapper или неоднозначном bank контекст помечается UNKNOWN без падения игры.

## 5. Stage AGOD-2: подтверждение событий и причинная проверка

Создать `CausalValidator`, используя существующие Save States, идентичность ROM/core/start и изолированные прогоны:

1. Сравнивать запуск **из одного состояния** при одинаковых контролируемых условиях: действие-кандидат, нейтральное действие, альтернативное допустимое действие.
2. Восстанавливать все доступные детерминирующие компоненты состояния эмулятора, включая RNG, если он сериализуется; учитывать остаточную недетерминированность и не заявлять причинность, если паритет восстановления не достигнут.
3. Проверять несколько стартов/траекторий, а не кадры одного rollout как независимую выборку.
4. Проверять, воспроизводится ли изменение при отсутствии действия; не считать таймеры, анимацию, звук, случайные RAM-счётчики и меню игровым успехом.
5. Отличать `score+` от `level+`, `death`, `lives-`, `respawn`, `reset`, `pause`, `high score` и побочных переменных. Подтверждать терминальность отдельно, а не выводить её из одного изменённого байта.
6. Учитывать устойчивость семантики события при разных интенсивностях действий и на удержанных состояниях; фиксировать неоднозначность и противоречивые наблюдения.
7. Сохранять доказательства, версию детектора и ROM/core hash; при обновлении ROM/core/config профиль требует повторной валидации.

**Ключевой запрет:** автоматический детектор не должен подбирать правило награды на тех же контрольных состояниях, которые затем используются для Frozen Evaluation / BestPromotionGate. Discovery, calibration и held-out evaluation должны иметь непересекающиеся группы происхождения. Поиск множества гипотез учитывать как множественную проверку; не применять чисто номинальную p-value как универсальное доказательство.

Порог допуска задавать предварительно в тестовом протоколе, с минимальным числом независимых проверок, допустимым уровнем ложных событий и калибровкой confidence. Произвольное `0.9` без измерения не принимать за достоверность.

## 6. Stage AGOD-3: RewardSynthesizer и интеграция в FDB

После подтверждения событий реализовать `RewardSynthesizer`, **не подменяя существующую пластичность**:

- `VERIFIED score/progress`: bounded положительная награда за достоверный прирост с проверкой сброса/накопления; не поощрять повторное наблюдение одного события.
- `VERIFIED death/life loss`: ограниченная отрицательная награда, только при подтверждённом переходе. Не считать отсутствие прогресса смертью или ошибкой.
- `VERIFIED goal/level complete`: эпизодическое событие с подтверждённой границей; исключить дублирующие бонусы за связанные RAM-переменные.
- `UNKNOWN`: **ни reward, ни reward=0, ни terminal**. Сохранять диагностическое событие и закрывать временную привязку через уже реализованный безопасный FDB boundary, если невозможно соотнести исход с конкретным действием.
- Нулевая награда допустима только для наблюдённого, валидного интервала с явно известной семантикой отсутствия вознаграждаемого события; не использовать её как значение по умолчанию для пропущенного наблюдения.
- Ввести idempotency по eventId/context/generation/action window; предотвращать повторную отправку одного результата.
- Вознаграждение привязывать к **фактически исполненному нейронному действию** и frame/time интервалу из `fdb-feedback.js`, не к последнему запрошенному, но ещё не исполненному действию. Ручное вмешательство и рассинхронизация делают causal-credit недействительным.
- Если подтверждение пришло позже максимального окна текущей eligibility, **не назначать награду случайному последнему решению**. Сохранить событие на уровне эпизода и отметить необходимость отдельной архитектуры delayed credit для будущего раунда.
- Не передавать RAM, PC или writer-site как скрытую дополнительную сенсорную информацию в нейронную политику. Это оценщик, а не читерский контроллер.

Добавить `rewardMode=auto-discovery` и машиночитаемый `rewardSource` при сохранении backward compatibility с текущими `manual`, `ram`, `score`, `diagnostic`. Для обычного пользователя: Auto / Searching / Verified / Not enough evidence / Unsupported, без ручного указания адресов.

В `autonomous-episodes.js` заменить только hard-coded допуск к источнику награды на проверку совместимого `RewardEvidence`/verified profile. Сохранять и использовать действующие CurriculumStore, FrozenSeries, EvaluationArchive, EpisodeHistory и BestPromotionGate. `Best` не повышать по одной исследовательской novelty-награде.

## 7. Внутренняя исследовательская мотивация (отдельно от внешней награды)

Допускается ограниченный **intrinsic exploration score** за новое, устойчивое, зависимое от действий состояние только в discovery/train. Его необходимо хранить в отдельном канале с `source=intrinsic`, пределом на повтор одного состояния и штрафом/фильтром за счётчики времени, кнопочные эхо-значения и шум.

Не смешивать `intrinsic` с доказанными результатами игры. Не использовать intrinsic для frozen external-success или повышения Best. По умолчанию выключить его влияние на FDB reward до отдельного парного теста против `intrinsic=off` и измерения reward hacking. На первой итерации допустим **только исследовательский рейтинг**, без изменения весов.

## 8. Производительность, безопасность и восстановление

- Основная эмуляция в штатном режиме должна работать без дорогой трассировки; замерить overhead при discovery и при обычной игре: FPS, frame-time p50/p95/p99, долю времени инструментирования, память, буферы, dropped events, батарею на реальном Android.
- Пределы размера RAM snapshot, trace buffer, очередей, диска и TTL. Бэкпрешер: сброс трасс/приостановка discovery без остановки самой игры и без поддельной награды.
- При `pause`, ROM/core смене, save/load, manual override, freeze, потере окна/фона, аварии или изменении поколения отменять pending hypotheses/rewards и очищать несопоставимые eligibility через подтверждённый boundary.
- Обнаруженный профиль сохранять отдельно от Learned Layer; привязка минимум `(platform, ROM hash, core revision, detector schema, reward-profile revision)`, без переноса на чужой ROM.
- Секретов и облачных сетевых обращений нет; снимки RAM/CPU trace хранятся локально и по запросу удаляются. Отдельная функция экспорта диагностического отчёта без дампа приватной памяти по умолчанию.
- Ошибка анализатора не должна ломать ручной эмулятор, загруженную игру, Current/Best/Recovery или активный контроллер. Никакого незаметного fallback на manual с «успешным обучением».

## 9. Обязательные тесты

Создать открытый собственный/лицензионно допустимый NES test ROM с **заведомо известной программной логикой** и тестами:

1. Счёт +1 при подтверждённом событии; monotonic frame counter и таймер не проходят допуск.
2. Потеря жизни и reset/respawn; переход `lives-` не путается с изменением адреса счёта.
3. Level transition и отдельный терминальный маркер; нет двойного начисления за одно событие.
4. Несколько writer-PC и банков ROM (если тестовый mapper это поддерживает); корректная provenance и UNKNOWN при отсутствии банкового соответствия.
5. Повторный запуск из одного Save State с action/neutral/alternative; одинаковый outcome воспроизводится только при ожидаемом действии.
6. Контрпример: счётчик меняется без действий; награда отсутствует.
7. Контрпример: меню/заставка/таймер имитирует прогресс; система остаётся UNKNOWN.
8. Контрпример: значение совпало случайно один раз, затем перестало воспроизводиться; профиль не проходит promotion.
9. Любой UNKNOWN/trace overflow/boundary не меняет ΔW/Wexo/baseline; подтвердить полным fingerprint до/после.
10. Идемпотентность при дубле bridge callback, смене ROM и загрузке Save State во время подтверждения.
11. Frozen evaluation не меняет полное состояние FDB; контрольные старты не участвовали в discovery/tuning.
12. Проверка `Current/Best/Recovery`: без независимого улучшения Best не обновляется, даже если растёт intrinsic score.
13. Калибровка overhead и деградация при отключении tracing; прежние тесты NES emulation/save/load проходят без изменения результатов.
14. Реальный Android: длительная сессия с включённым discovery, фон/возврат, расход памяти и CPU, без регрессии ручного управления.

Для тестов всегда сообщать отдельно: unit, host-emulator, controlled ROM, frozen generalization, physical Android. Не заменять последние две категории CI-прохождением на хосте.

## 10. Разбивка исполнения и stop-gates

**PR1: AGOD Foundation + GameGoalInduction cold-start contract.** Read-only `GameObservation` + RAM candidate miner + формат отчёта + тестовый ROM; пока никакой FDB reward. **Gate:** детектируются известные RAM-кандидаты, контрольные таймеры отвергаются, зафиксированы формат GameObjectiveProfile и нулевой ручной ввод в потребительском cold start; старая эмуляция проходит regression.

**PR2: Instrumented NES.** Opt-in CPU write trace с PC/bank provenance, watchpoints и ограничениями ресурсов. **Gate:** known writer-sites корректны, неизвестные помечены UNKNOWN, fast-path сохраняет поведение, замерен overhead.

**PR3: Evidence & Causal Validation.** Сравнительные независимые прогоны и реестр доказательств, train/calibration/holdout partition. **Gate:** низкая ложноположительная частота на заранее подготовленных контрпримерах, отсутствие contamination.

**PR4: Verified Reward Bridge.** RewardSynthesizer, context/sequence/idempotency, UI status, интеграция с текущим FDB и AutonomousEpisodes. **Gate:** валидный результат обновляет существующий FDB один раз, UNKNOWN не обновляет, frozen не меняется, Best не продвигается без независимого контроля.

**PR5 (после приёмки):** профилирование Android и ограниченное включение в пользовательский Auto для поддерживаемых NES ROM. Другие платформы и intrinsic FDB reward только по отдельному решению.

После каждого PR Codex предоставляет: base/head commit, изменённые файлы, точную команду тестирования, сырой отчёт, benchmark с условиями, известные ложные срабатывания, ограничения и статус `PASS / FAIL / DEVICE-PENDING`. Изменять PR scope без согласования не нужно. Автоматическое слияние в main запрещено.

## 11. Итоговый критерий приёмки

На контролируемом NES ROM GU **без ручного указания RAM-адресов** самостоятельно:

1. Обнаруживает кандидатов на игровые события из изменяющейся RAM.
2. Показывает происхождение записей в памяти через трассируемые CPU writer-sites там, где это доступно.
3. Отделяет действительные события от таймеров и случайного шума по повторяемости и контрольным действиям.
4. Формирует ограниченную награду только по событиям, прошедшим установленный gate.
5. Передаёт эту награду существующей FDB-системе с правильной временной привязкой и без повторов.
6. Сохраняет опыт между игровыми отрезками, не изменяет веса при UNKNOWN/frozen и не повышает Best без независимой проверки.
7. Не ухудшает обычную эмуляцию и корректно отключает discovery при превышении ресурсов.

**Запрещённый вывод:** «GU автоматически понимает цели любой игры по байткоду», «каждое изменение RAM полезно» или «создан универсальный анализатор» на основании единственного специально подготовленного ROM.
**Допустимый проверенный вывод после успешной приёмки:** «GU может автономно открывать и проверять некоторые игровые события через наблюдение исполнения и состояния NES, используя подтверждённые результаты для обучения нейронного агента».

## Приложение v1.2: дополнительные stop-gates для Codex

- **Gate S0: никаких ручных задач на ROM.** UI-путь открытия незнакомого ROM не запрашивает функцию награды, RAM-адрес или оценку действия; сохранены обычная игра и понятный `UNKNOWN`.
- **Gate S1: доказательство обобщения.** Детектор успешно работает хотя бы на нескольких отличающихся, заранее не размеченных для него ROM/сценариях. Эталонный test-oracle не импортируется в production.
- **Gate S2: доказательство причинности.** Положительные/отрицательные reward не возникают на негативных контролях (таймер, dummy counter, отсутствие действия, смена меню, повтор одного события); причины false positives сохраняются в отчёте.
- **Gate S3: доказательство цены.** В штатной игре с VERIFIED-профилем нет постоянного CPU instruction trace. Сравнение p95/p99 и батареи на мобильном устройстве обязательно до включения default-on.
- **Gate S4: доказательство обучения.** Измерять раздельно качество обнаружения цели, FDB weight updates и поведенческое улучшение на frozen holdouts. Первые два факта не заменяют третий.

**Полномочие этой редакции:** v1.2 заменяет v1.1 как исполнительное ТЗ AGOD, не отменяет завершённый исследовательский handoff A/B/A2/A3 и не разрешает автоматическое изменение/слияние production-кода без прохождения stop-gates.
